# Contracts

Contracts the operator owns or depends on. Changing one updates its entry in the same PR.

### Endpoint status conditions (`ExternalEndpointReady`, `InternalEndpointReady`)
**Owner:** `operator/internal/controller` · **Consumers:** the docs site (`architecture.mdx`, `configuration.mdx`), unit and envtest tests in the same package, humans via `kubectl`; once the reconcilers are wired, `endpointCondition` reads the endpoint's previous condition (status, reason, `lastTransitionTime`) back from the model (verified: `rg -l "EndpointReady|RouteNotAccepted|RoutePending|RouteStatusUnreadable" --glob '!node_modules' --glob '!.worktrees' .`). The `operator/test/e2e/e2e_test.go` hit is `verifyMetricsEndpointReady`, unrelated.
**Promises:** Applies to LLMModel and PassthroughModel. Status is `True`, `False` or `Unknown`. Reasons today are `Applied`, `EndpointDisabled`, `ApplyFailed` and `GatewayCRDUnavailable`. The reasons `RoutePending` (`Unknown`), `RouteNotAccepted` (`False`) and `RouteStatusUnreadable` (`Unknown`) are defined and are emitted once the PassthroughModel and LLMModel reconcilers call `endpointCondition`. When emitted, `Applied` means the Gateway accepted the route, and `lastTransitionTime` comes from the reconciler's `Clock`. An LLMModel endpoint condition covers the route only; a PassthroughModel endpoint condition covers route and policy together. A disabled endpoint is `False/EndpointDisabled` and is not a failure. No program outside the operator parses the reasons.
**Since:** 2026-11-20 (issue #233)

### `status.phase` of LLMModel and PassthroughModel
**Owner:** `operator/internal/controller` · **Consumers:** `dev/run-dev.sh:85`, `dev/usage-e2e.sh:135,163`, `dev/test-model-scope.sh:131-132` (all `kubectl wait ... phase=Ready`), the docs site (verified: `rg -n "status\.phase" --glob '!node_modules' --glob '!.worktrees' --glob '!operator/**' --glob '!docs/**' --glob '!charts/**/crds/**' .`)
**Promises:** Same enum as today. The new route-acceptance reasons do not change the phase yet. An apply failure or `GatewayCRDUnavailable` downgrades LLMModel `Ready` to `Degraded` and gives PassthroughModel `Error`. Once the reconcilers call `endpointCondition`, `RouteNotAccepted` is treated as a gateway failure (LLMModel `Degraded`, PassthroughModel `Error`), while `RoutePending` and `RouteStatusUnreadable` leave `Ready` untouched, so the scripts' `wait ... phase=Ready` behave as before on a healthy cluster.
**Since:** 2026-11-20 (issue #233)

### Generated HTTPRoute
**Owner:** Envoy AI Gateway and Envoy Gateway (external) · **Consumers:** `removeEndpoint` (`passthroughmodel_endpoints.go:30`), `readRouteAcceptance` (`route_acceptance.go:86`) (verified: `rg -n '"HTTPRoute"' operator --glob '!*_test.go'`)
**Promises:** Same name and namespace as its AIGatewayRoute. `spec.parentRefs` and `spec.hostnames` are copied from the AIGatewayRoute (ai-gateway v1.1.0 `internal/controller/ai_gateway_route.go:368-370`). `status.parents[]` is written by Envoy Gateway, with the `Accepted` condition's `observedGeneration` set to the HTTPRoute generation. The `reconcilers/auth.go` hits are `targetRefs` the pack writes, not reads.
**Since:** 2026-11-20 (issue #233)

### AIGatewayRoute `status.conditions`
**Owner:** Envoy AI Gateway (external) · **Consumers:** `readRouteAcceptance`, via `aiGatewayNotAcceptedMessage` (`route_acceptance.go`), for the message only (verified: `rg -n "NotAccepted" operator --glob '!*_test.go'`)
**Promises:** At most one condition, of type `Accepted` (True) or `NotAccepted` (False), with no `observedGeneration`. The operator reads it only for its message, never to decide a status or reason (ai-gateway v1.1.0 `internal/controller/controller.go:551-566`, `api/v1beta1/status.go:13-16`). `readRouteAcceptance` is the only reader, through `aiGatewayNotAcceptedMessage`, which returns the message of the first `NotAccepted=False` or `Accepted=False` condition; the other hits are the reason constants in `conditions.go` and comments.
**Since:** 2026-11-20 (issue #233)

### `gatewayRequeue`, `hasGatewayFailure`, `phaseWithGatewayFailure`
**Owner:** `operator/internal/controller/conditions.go` · **Consumers:** `llmmodel_controller.go:226,233`, `conditions.go` itself, and the PassthroughModel requeue (`gatewayRequeue`) once wired (verified: `rg -n "gatewayRequeue\(|hasGatewayFailure\(|phaseWithGatewayFailure\(" operator --glob '!*_test.go'`)
**Promises:** Signatures are unchanged. `gatewayRequeue` returns the shortest interval any condition asks for, keyed on reason: `RoutePending` 5 s, `GatewayCRDUnavailable` 15 s, `RouteStatusUnreadable` 15 s, `RouteNotAccepted` 1 min, `ApplyFailed` 1 min, otherwise 0. It considers `Unknown` conditions as well as `False`, and ignores reasons it does not know (so `UpstreamCredentialResolved=Unknown/LookupFailed` contributes nothing). `hasGatewayFailure` is true for a `False` condition whose reason is `GatewayCRDUnavailable`, `ApplyFailed` or `RouteNotAccepted`; `RoutePending` and `RouteStatusUnreadable` requeue without counting as failures. `phaseWithGatewayFailure` is unchanged and picks up `RouteNotAccepted` through `hasGatewayFailure`. Existing inputs give existing outputs.
**Since:** 2026-11-20 (issue #233)

### `endpointCondition`, `readRouteAcceptance`, `routeAcceptanceCondition`
**Owner:** `operator/internal/controller/route_acceptance.go` · **Consumers:** none yet; `LLMModelReconciler` and `PassthroughModelReconciler` will call `endpointCondition` (verified: `rg -n "endpointCondition\(" operator --glob '!*_test.go'` finds only the definition)
**Promises:** Implemented and unit-tested in `operator/internal/controller/route_acceptance.go`; no reconciler calls them yet (the PassthroughModel and LLMModel reconcilers adopt them in later changes). `readRouteAcceptance` reads the generated HTTPRoute for the applied AIGatewayRoute, matches the `status.parents[]` entry on the route's single parent ref (`name`, `namespace`, `sectionName`), and counts it only when the HTTPRoute is current (same hostnames and parent refs, `Accepted.observedGeneration` equal to the HTTPRoute generation). A NotFound HTTPRoute is "route not found", not an error. `routeAcceptanceCondition` and `endpointCondition` turn that observation into the endpoint condition, using a 2 minute creation window and a 2 minute previous-condition window to choose between `RoutePending` and `RouteNotAccepted`, and stamp `lastTransitionTime` from the injected clock. A failed apply is reported as `ApplyFailed` and no acceptance read happens. A read error that is a NoMatch error gives `False`/`GatewayCRDUnavailable`. Any other read error gives `Unknown`/`RouteStatusUnreadable` with the message `reading HTTPRoute status: <err>`, unless the previous condition is `False`/`RouteNotAccepted`: then it stays `False`/`RouteNotAccepted` with `; last status read failed: <err>` appended once (a repeated error replaces that suffix, so the message does not grow).
**Since:** 2026-11-20 (issue #233)
