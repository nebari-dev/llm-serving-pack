# Contracts

Contracts the operator owns or depends on. Changing one updates its entry in the same PR.

### Chart value `operator.webhook.clusterIssuer`
**Owner:** `charts/nebari-llm-serving` (`values.yaml`, `templates/operator-webhook-cert.yaml`) · **Consumers:** every chart install, through the webhook serving Certificate's `issuerRef`; the docs site (`configuration.mdx`, `installation.md`, `quickstart.mdx`, `upgrading.mdx`) and `README.md` (verified: `rg -n "operator\.webhook\.clusterIssuer|\.Values\.operator\.webhook" --glob '!node_modules' --glob '!.worktrees' .`). The kind dev cluster installs from `dev/manifests/`, not the chart, and is unaffected.
**Promises:** A string naming a cert-manager `ClusterIssuer` (the `kind` stays `ClusterIssuer`). It signs the operator's admission webhook serving Certificate, whose DNS names are `<svc>.<ns>.svc` and `<svc>.<ns>.svc.cluster.local`. Default `nebari-ca-issuer`, which NIC creates in releases that include nebari-infrastructure-core#787; before this value existed the issuer was hardcoded to `selfsigned-issuer`. A missing key or `operator.webhook` block (for example values reused from an older release with `helm upgrade --reuse-values`) renders the default. An explicitly empty value fails the render with `operator.webhook.clusterIssuer is required: ...`. The chart does not create the issuer.
**Since:** 2026-11-20

### Endpoint status conditions (`ExternalEndpointReady`, `InternalEndpointReady`)
**Owner:** `operator/internal/controller` · **Consumers:** the docs site (`architecture.mdx`, `configuration.mdx`), unit and envtest tests in the same package, humans via `kubectl`; `PassthroughModelReconciler` and `LLMModelReconciler` call `endpointCondition`, which reads the endpoint's previous condition (status, reason, `lastTransitionTime`) back from the model (verified: `rg -l "EndpointReady|RouteNotAccepted|RoutePending|RouteStatusUnreadable" --glob '!node_modules' --glob '!.worktrees' .`). The `operator/test/e2e/e2e_test.go` hit is `verifyMetricsEndpointReady`, unrelated.
**Promises:** Applies to LLMModel and PassthroughModel. Status is `True`, `False` or `Unknown`. Reasons today are `Applied`, `EndpointDisabled`, `ApplyFailed` and `GatewayCRDUnavailable`. The reasons `RoutePending` (`Unknown`), `RouteNotAccepted` (`False`) and `RouteStatusUnreadable` (`Unknown`) are emitted by both reconcilers. For both kinds, `Applied` means the Gateway accepted the route, and `lastTransitionTime` comes from the reconciler's `Clock`. An LLMModel endpoint condition covers the route only; a PassthroughModel endpoint condition covers route and policy together. A disabled endpoint is `False/EndpointDisabled` and is not a failure. No program outside the operator parses the reasons.
**Since:** 2026-11-20 (issue #233)

### `status.phase` of LLMModel and PassthroughModel
**Owner:** `operator/internal/controller` · **Consumers:** `dev/run-dev.sh:85`, `dev/usage-e2e.sh:140,168`, `dev/test-model-scope.sh:131-132` (all `kubectl wait ... phase=Ready`), the docs site (verified: `rg -n "status\.phase" --glob '!node_modules' --glob '!.worktrees' --glob '!operator/**' --glob '!docs/**' --glob '!charts/**/crds/**' .`)
**Promises:** Same enum as today. An apply failure or `GatewayCRDUnavailable` downgrades LLMModel `Ready` to `Degraded` and gives PassthroughModel `Error`. `RouteNotAccepted` is treated the same way: it gives LLMModel `Degraded` and PassthroughModel `Error`, while `RoutePending` and `RouteStatusUnreadable` leave `Ready` untouched on both. The scripts' `wait ... phase=Ready` behave as before on a healthy cluster.
**Since:** 2026-11-20 (issue #233)

### AIGatewayRoute `status.conditions`
**Owner:** Envoy AI Gateway (external) · **Consumers:** `readRouteAcceptance`, via `aiGatewayNotAcceptedMessage` (`route_acceptance.go`), for the message only (verified: `rg -n "NotAccepted" operator --glob '!*_test.go'`)
**Promises:** At most one condition, of type `Accepted` (True) or `NotAccepted` (False), with no `observedGeneration`. The operator reads it only for its message, never to decide a status or reason (ai-gateway v1.1.0 `internal/controller/controller.go:551-566`, `api/v1beta1/status.go:13-16`). `readRouteAcceptance` is the only reader, through `aiGatewayNotAcceptedMessage`, which returns the message of the first `NotAccepted=False` or `Accepted=False` condition; the other hits are the reason constants in `conditions.go` and comments.
**Since:** 2026-11-20 (issue #233)

### `gatewayRequeue`, `hasGatewayFailure`, `phaseWithGatewayFailure`
**Owner:** `operator/internal/controller/conditions.go` · **Consumers:** `llmmodel_controller.go:233,246`, `conditions.go` itself, and the PassthroughModel requeue (`gatewayRequeue`, `passthroughmodel_controller.go:230`) (verified: `rg -n "gatewayRequeue\(|hasGatewayFailure\(|phaseWithGatewayFailure\(" operator --glob '!*_test.go'`)
**Promises:** Signatures are unchanged. `gatewayRequeue` returns the shortest interval any condition asks for, keyed on reason: `RoutePending` 5 s, `GatewayCRDUnavailable` 15 s, `RouteStatusUnreadable` 15 s, `RouteNotAccepted` 1 min, `ApplyFailed` 1 min, otherwise 0. It considers `Unknown` conditions as well as `False`, and ignores reasons it does not know (so `UpstreamCredentialResolved=Unknown/LookupFailed` contributes nothing). `hasGatewayFailure` is true for a `False` condition whose reason is `GatewayCRDUnavailable`, `ApplyFailed` or `RouteNotAccepted`; `RoutePending` and `RouteStatusUnreadable` requeue without counting as failures. `phaseWithGatewayFailure` is unchanged and picks up `RouteNotAccepted` through `hasGatewayFailure`. Existing inputs give existing outputs. While an LLMModel's `SecurityPoliciesReady` is pending, the LLMModel reconciler returns a flat 15 s (`gatewayCRDRequeue`, `llmmodel_controller.go:243-245`) before consulting `gatewayRequeue`, so a `RoutePending` endpoint is rechecked at 15 s then, not 5 s.
**Since:** 2026-11-20 (issue #233)

### `endpointCondition`, `readRouteAcceptance`, `routeAcceptanceCondition`
**Owner:** `operator/internal/controller/route_acceptance.go` · **Consumers:** `PassthroughModelReconciler` (`passthroughmodel_controller.go:157,173`) and `LLMModelReconciler` (`llmmodel_controller.go:217,224`) (verified: `rg -n "endpointCondition\(" operator --glob '!*_test.go'` finds the definition and those four calls)
**Promises:** Implemented and unit-tested in `operator/internal/controller/route_acceptance.go`; both reconcilers call `endpointCondition` for each enabled endpoint. `readRouteAcceptance` reads the generated HTTPRoute for the applied AIGatewayRoute, matches the `status.parents[]` entry on the route's single parent ref (`name`, `namespace`, `sectionName`), and counts it only when the HTTPRoute is current (same hostnames and parent refs, `Accepted.observedGeneration` equal to the HTTPRoute generation). A NotFound HTTPRoute is "route not found", not an error. `routeAcceptanceCondition` and `endpointCondition` turn that observation into the endpoint condition, using a 2 minute creation window and a 2 minute previous-condition window to choose between `RoutePending` and `RouteNotAccepted`, and stamp `lastTransitionTime` from the injected clock. A failed apply is reported as `ApplyFailed` and no acceptance read happens. A read error that is a NoMatch error gives `False`/`GatewayCRDUnavailable`. Any other read error gives `Unknown`/`RouteStatusUnreadable` with the message `reading HTTPRoute status: <err>`, unless the previous condition is `False`/`RouteNotAccepted`: then it stays `False`/`RouteNotAccepted` with `; last status read failed: <err>` appended once (a repeated error replaces that suffix, so the message does not grow).
**Since:** 2026-11-20 (issue #233)

### `versions.env` file format
**Owner:** `versions.env` at the repo root, parsed by `ParsePins` in `operator/cmd/render-pins/pins.go` · **Consumers:** `dev/Makefile` (`include ../versions.env`), `render-pins`, `.github/workflows/test.yaml` (the AI Gateway CRD render step reads `AI_GATEWAY_VERSION`; the `Check default images` job runs `render-pins --check`), the `paths` filter of `.github/workflows/docs.yml`, `scripts/check-render-determinism.sh` (`CHART_VERSION`), and the version case in `docs/test/docs-examples.test.mjs`. The docs pin plugin and the journey suite read it in later slices and are not consumers yet (verified: `rg -n "versions\.env" --glob '!node_modules' --glob '!.worktrees' --glob '!docs/superpowers/**' .`).
**Promises:** One `KEY=value` per line, `#` comment lines and blank lines allowed, no quotes, no spaces around `=` or in a key, no `$` expansion, no duplicate keys, so that make `include`, `grep` and the Go parser all read the same value. Keys today: `CERT_MANAGER_VERSION`, `GATEWAY_API_VERSION`, `GIE_VERSION` (v1.5.0; `dev/Makefile` had v1.4.0), `ENVOY_GATEWAY_VERSION`, `AI_GATEWAY_VERSION`, `USAGE_COLLECTOR_IMAGE`, `OPENMETER_IMAGE`, `CNPG_CHART_VERSION`, `CNPG_IMAGE_TAG`. The two `*_IMAGE` keys hold `repository:tag@digest`. `ENVOY_GATEWAY_VERSION` and `AI_GATEWAY_VERSION` are written into the published examples; `USAGE_COLLECTOR_IMAGE` and `OPENMETER_IMAGE` into the chart values (see the `render-pins` entry); the others are read only by `dev/Makefile`. The AI Gateway, Envoy Gateway and Gateway API versions move together. Adding a key changes this entry in the same PR.
**Errors:** `render-pins` rejects a line with no `=`, an empty key, a quote, a `$`, spaces around `=`, or a repeated key, naming the line number; a key a template names but the file lacks fails the render.
**Since:** 2026-11-26 (docs/superpowers/specs/2026-11-24-ci-journey-tests-design.md)

### `render-pins` CLI and exit code
**Owner:** `operator/cmd/render-pins/` · **Consumers:** developers, `make render-pins` (`dev/Makefile:40`), and the `Check default images` job in `.github/workflows/test.yaml` (verified: `rg -n "render-pins" --glob '!node_modules' --glob '!.worktrees' --glob '!docs/superpowers/**' --glob '!operator/cmd/render-pins/**' .`)
**Promises:** Run as `cd operator && go run ./cmd/render-pins --root <repo root>`. `--root` is required. Without `--check` it rewrites each generated file that differs from what `versions.env` renders, prints `WROTE <path>` for each, and writes nothing else (a fresh tree is a no-op). With `--check` it writes nothing, prints `STALE <path>` for each stale file on stdout, and exits 1 if any. Exit codes: 0 fresh or written, 1 a read, parse or render failure or stale files under `--check`, 2 a usage error (bad flag or missing `--root`). The generated set is the two examples and the two chart image fields (see the entries above); adding one changes this entry.
**Errors:** Messages go to stderr as `ERROR: <cause>`; a stale check ends with `N generated file(s) stale; run: go run ./cmd/render-pins --root <root>`.
**Since:** 2026-11-26 (docs/superpowers/specs/2026-11-24-ci-journey-tests-design.md)

### `tests/journeys/features.toml` schema
**Owner:** `tests/journeys/features.toml`, read by `tests/journeys/llm_journeys/features.py` · **Consumers:** the collection hook in `tests/journeys/journeys/conftest.py` (`load_features`, `load_known_failures`, `known_failure_problems`, `coverage_gaps`) and `llm_journeys.report` (`load_features`, `load_known_failures`) (verified: `rg -n "load_features\(|load_known_failures\(" tests/journeys --glob '*.py' --glob '!**/tests_lib/**'` finds the two definitions, the hook and the report).
**Promises:** One table per feature, keyed by ID (`[F5]`), with `title` (string) and `tiers` (array of `integration`, `journey`, `release`). IDs are stable and never reused. The top-level key `known_failures` is reserved and is not a feature; it is a list of entries `{ test, issue, since, targets }`. `test` is the pytest node ID relative to `tests/journeys/`, keyed per test. `issue` is required. `targets` is optional; empty or absent means every target the test's tiers run on (`kind-dev` for `integration`, `nebari` for `journey` and `release`). An entry has no effect on a target it does not list. A listed test still runs and is never skipped or deselected. The file is the committed copy of the spec's Features table, because the spec is gitignored. Collection checks the entries on the full collected set, before any deselection by tier, `--feature` or `--release-stage`, so a narrowed run does not reject an entry for a test it does not select.
**Errors:** `load_features` raises `ValueError` for a tier outside the three names, and `KeyError` for a feature table without `title` or `tiers`. Collection exits with `INTERRUPTED` (pytest exit 2) for a known-failure entry with no `issue`, an entry whose `test` matches no collected test, and an entry naming a target its test does not run on.
**Since:** 2026-11-26 (spec: docs/superpowers/specs/2026-11-24-ci-journey-tests-design.md)

### pytest interface: markers `feature`, `integration`, `journey`, `release`; options `--target`, `--kube-context`, `--gateway-https-port`, `--feature`, `--release-stage`, `--state`
**Owner:** `tests/journeys/conftest.py` (options), `tests/journeys/journeys/conftest.py` (collection hook), `tests/journeys/pytest.ini` (markers, `--strict-markers`) · **Consumers:** `tests/journeys/run-suite.sh` (passes `--junitxml` and `--feature`); the make targets, pixi tasks and phase 2 workflows do not exist yet and will call it (verified: `rg -n "addoption|pytest_collection_modifyitems|^markers|strict-markers" tests/journeys --glob '*.py' --glob '*.ini' --glob '!**/tests_lib/**'`).
**Promises:** Every test under `tests/journeys/journeys/` carries exactly one `@pytest.mark.feature("F<n>")` naming an ID in `features.toml`, and at least one of `integration`, `journey` or `release`. `--target=kind-dev|nebari` selects the `integration` or `journey` tier. `--release-stage=before|after` is valid only with `--target=nebari` and `--state PATH`, and selects tests marked `@pytest.mark.release("before")` or `release("after")` instead of the journey tier. Tests outside the selection are deselected, never skipped. `--feature F4,F8` narrows the run to those IDs; it fails if an ID is not in `features.toml` or has no test in the tier the run selects. `--kube-context` names the context for every cluster call. `--gateway-https-port` is an int; its documented default is 48443 on `kind-dev` and 443 on `nebari`. On an unfiltered run (no `--feature`, no `--release-stage`), collection fails when a feature has no test in one of its `features.toml` tiers. F11 tests are always moved to the end of the run, since F11 changes the operator's gateway setting. The root `conftest.py` makes every option optional so `pytest tests_lib` runs with no arguments. At this slice the hook does not yet check that `--target` and `--kube-context` are set; the session fixtures that fail when they are unset arrive with the journey tests. No test calls `pytest.skip` or `xfail`.
**Errors:** Collection exits with `INTERRUPTED` (pytest exit 2) and a `collection failed:` list for a test with no or several feature markers, an ID absent from `features.toml`, no tier marker, a malformed `release` marker, a known-failure problem, or, on an unfiltered run, a coverage gap. A bad `--feature` value, or `--release-stage` without `--target=nebari` and `--state`, is a `pytest.UsageError` (pytest exit 4).
**Since:** 2026-11-26 (spec: docs/superpowers/specs/2026-11-24-ci-journey-tests-design.md)

### JUnit XML and `run-info.json` written by a suite run
**Owner:** `tests/journeys/journeys/conftest.py` (the `<testcase>` properties); `run-info.json` is written at session end by the suite (not in this slice) · **Consumers:** `llm_journeys.report` (reads both; `run-info.json` through `--run-info`), `tests/journeys/run-suite.sh` (pytest writes `results/junit.xml`; the report reads `results/run-info.json`) (verified: `rg -n "user_properties.append|run-info|run_info" tests/journeys --glob '*.py' --glob '*.sh' --glob '!**/tests_lib/**'`).
**Promises:** Each `<testcase>` of a test under `tests/journeys/journeys/` carries these properties, attached with `item.user_properties` in `pytest_collection_modifyitems` after deselection, so they are in the JUnit file even when a session fixture raises before a test body runs: `nodeid` (the pytest node ID relative to `tests/journeys/`, which `known_failures` matches on), `feature` (the ID), `tiers` (the tier markers, sorted and comma-joined, such as `integration,journey`), and `stage` (`before` or `after`, only on `release` tests). The report ignores a testcase with no `feature` property, and treats a `feature` without `nodeid` or a `stage` outside `before`/`after` as a usage error. `pytest.ini` sets `junit_family = xunit2`. `run-info.json` is a JSON object with these keys: `target` (string, required; the report fails with exit 2 when it is missing or empty); `kube_context` (the context the run used); `nic_tag` (the NIC tag, or null); `before_nic_tag` (on a `--release-stage=after` run, the NIC tag of the `before` run, copied from the release state file); `helper` (object `{tag, commit}`, the `nebari_journeys` source actually installed, from `results/helpers.json`); `components` (object `{name: version}`, the installed versions of components NIC provides, such as Envoy Gateway and cert-manager, read from the cluster); `deviations` (list of strings, each shown in the report). Only `target` is required; the report prints the others when present.
**Errors:** A JUnit file that is missing or not valid XML, and a `run-info.json` that is missing, not JSON or lacks `target`, make the report exit 2.

### `python -m llm_journeys.report` CLI and exit code
**Owner:** `tests/journeys/llm_journeys/report.py` · **Consumers:** `tests/journeys/run-suite.sh`; the make targets, pixi tasks and phase 2 workflows will call it through `run-suite.sh` (verified: `rg -n "llm_journeys.report" tests/journeys --glob '*.sh' --glob '*.py' --glob '!**/tests_lib/**'`).
**Promises:** `python -m llm_journeys.report --junit PATH [--junit PATH ...] --features PATH --pins PATH --run-info PATH --tier integration|journey|release [--feature F10,F12] [--strict-known-failures] [--out PATH]`. It reads the JUnit files, `features.toml`, `versions.env` and `run-info.json`, and writes a markdown table by feature ID to stdout, or to `--out`, followed by the run, pin and deviation sections. Results for a feature are merged across files: a feature passes only when every one of its tests in every file passed. In the `release` tier it passes only when both a `before` and an `after` result are present. Outcomes are `passed`, `failed`, `not run` and `known failure (<issues>)`; JUnit `error` and `skipped` count as `failed`. A feature is `known failure` only when it has a failing test and every failing test is listed for the run's target (from `run-info.json`); an unlisted failing test makes it `failed`. `--feature` limits the report to those IDs, which must be in `features.toml` and in `--tier`. Exit codes: 1 when a reported feature is `failed` or `not run`; 1 when a listed known-failure test passes and `--strict-known-failures` is set, otherwise a `Warning:` line in the output and no change to the exit code; 2 on a usage error; otherwise 0. The run status rule lives in `run-suite.sh`: pytest's exit code is captured and the report always runs; the final status is the report's code when pytest exited 0 or 1, and pytest's own code when it exited 2 to 5.
**Errors:** Exit 2, with `llm_journeys.report: <reason>` on stderr, for a missing required option, an unknown `--tier`, a missing or unreadable input file, malformed TOML, JSON, XML or `versions.env`, an unknown `--feature` ID or one outside the tier, and a `run-info.json` without `target`.
**Since:** 2026-11-26 (spec: docs/superpowers/specs/2026-11-24-ci-journey-tests-design.md)
