Every upgrade follows the [routine steps](#routine-upgrade). Some releases also
need [release-specific steps](#release-specific-steps), listed newest first:
read every entry between your current version and the target before you start.

## Routine upgrade

Read the [release notes](https://github.com/nebari-dev/llm-serving-pack/releases)
for every version between your current version and the target first. Confirm
the target chart is available before changing the Application:

```bash
helm show chart oci://quay.io/nebari/charts/nebari-llm-serving --version <version>
```

A GitHub Release can appear before its chart is published. Pointing ArgoCD at
an unavailable version reports `Sync: Unknown` with a `ComparisonError`, even
while health still shows `Healthy`. Wait for chart publication before proceeding;
see the [release publication caveat in the README](https://github.com/nebari-dev/llm-serving-pack#releasing).

Bump `targetRevision` in the pack's ArgoCD Application
([Installation section 8.1](/installation/#81-add-the-argocd-application)) to
the new chart version, push, and re-apply the Application with `kubectl apply -f`
(or let your app-of-apps sync it). Pushing alone does not update an Application
that was installed manually. With `automated` sync on, ArgoCD then rolls it out;
otherwise sync it by hand.

**CRDs.** The chart ships the `LLMModel` and `PassthroughModel` CRDs in
its `crds/` directory. ArgoCD applies them on every sync, so they move
with the operator as long as the Application does not set
`skipCrds: true`. Plain `helm upgrade` installs `crds/` only on first
install and never updates it, so a Helm-managed install must apply the
CRDs from the target release before upgrading:

```bash
helm pull oci://quay.io/nebari/charts/nebari-llm-serving --version <version> --untar
kubectl apply --server-side --force-conflicts -f nebari-llm-serving/crds/
kubectl wait --for=condition=Established --timeout=60s \
  crd/llmmodels.llm.nebari.dev crd/passthroughmodels.llm.nebari.dev
helm upgrade nebari-llm-serving oci://quay.io/nebari/charts/nebari-llm-serving \
  --version <version> -n nebari-llm-serving-system -f <your-values>.yaml
```

For a plain Helm install, `--force-conflicts` transfers ownership of the CRD
schema fields from Helm to `kubectl`: Helm owns them from the initial install
but does not update them during upgrades. If a separate tool manages the CRDs
(such as a GitOps repository or platform CRD pipeline), update them through
that tool instead of forcing ownership away from it.

Stop if the CRD apply fails. An old CRD can still report `Established`, and
`helm upgrade` can succeed while leaving its schema unchanged.

If the CRDs lag behind the chart, the API server keeps validating against
the old schema: fields the release added are rejected or dropped, so those
features do not work until the CRDs are updated.

:::caution[Never delete a CRD to upgrade it]
Deleting a CRD deletes every resource of that kind. Removing the
`LLMModel` or `PassthroughModel` CRD removes every model, and their
cleanup deletes the API keys users minted for them.
:::

Then re-run the checks in
[Installation section 8.2](/installation/#82-verify-the-install).

## Release-specific steps

Newest first. A release with no entry needs only the routine steps.

A release that changes a behavior listed on
[Extending the gateway](/extending-the-gateway/) names its ID (C1 to C4) in
its heading here, says what changed, and says what a deployment that relies on
it must do.

### Upgrading from 0.1.4 or earlier: the webhook certificate issuer

The ClusterIssuer that signs the operator's admission webhook certificate
is now the chart value `operator.webhook.clusterIssuer`, and its default
changed from `selfsigned-issuer` to `nebari-ca-issuer`. NIC creates
`nebari-ca-issuer` in releases that include
[nebari-infrastructure-core#787](https://github.com/nebari-dev/nebari-infrastructure-core/pull/787).

Check which issuers the cluster has:

```bash
kubectl get clusterissuer
```

If `nebari-ca-issuer` is listed with `READY=True`, no change is needed:
cert-manager reissues the webhook certificate from it right away and
updates the webhook's CA bundle. The operator picks up the new certificate
only when the kubelet next syncs its Secret volume, about a minute later.
In that window, creating or updating an `LLMModel` or `PassthroughModel`
fails with `x509: certificate signed by unknown authority`; retry after
a minute.

Otherwise, **keep the old issuer before upgrading** by adding it to your
values:

```yaml
operator:
  webhook:
    clusterIssuer: selfsigned-issuer
```

If you upgrade with neither, cert-manager leaves the existing certificate
Secret untouched, the Certificate goes `Ready=False` with reason
`IncorrectIssuer`, and its CertificateRequest stays `Pending`. Admission
keeps working with the old certificate, so the upgrade looks healthy, but
the certificate cannot be renewed and admission fails once it expires.
Create the issuer or set the value to fix it.

### Upgrading from 0.1.4 or earlier: access groups compared as group paths

`access.groups` is now compared with the token's groups claim as Keycloak
group paths (`auth.oidc.groupsClaimForm: path`, the default). The operator
writes each group as a path in the gateway's claim rule, so a model with
`access.groups: [ops]` only allows tokens whose claim carries `/ops`. The key
manager compares the same way.

NIC's realm already puts group paths in tokens, so a default NIC install needs
nothing. An install whose tokens carry plain names (`ops`) does: after the
upgrade the internal endpoint returns 403 for those users, while the key
manager still lists the model for them.

Check what the claim carries in a user's access token (replace `groups` if you
set `auth.oidc.groupsClaim` to another claim):

```bash
echo "$TOKEN" | jq -R 'split(".")[1] | gsub("-";"+") | gsub("_";"/") | @base64d | fromjson | .groups'
```

If the values start with `/`, nothing changes. Otherwise, before upgrading:

- **The claim is a role claim** (for example `auth.oidc.groupsClaim:
  realm_access.roles`): set `auth.oidc.groupsClaimForm: name`. Values are
  then compared exactly as written, as before.
- **The claim comes from a group membership mapper with "Full group path"
  off:** turn it on (`full.path: true`) in that mapper, so tokens carry
  `/ops`. `access.groups` can stay as `ops` or `/ops`. A user in a nested
  group such as `/org/ops` no longer matches `ops`; list the nested group by
  its full path. The chart sets this on the key manager's own client from
  `auth.oidc.groupsClaimForm`, so only mappers you manage need the change.

### Upgrading from 0.1.4 or earlier: gateway and issuer defaults

Two defaults now match what NIC creates:

| Value | Old default | New default |
|-------|-------------|-------------|
| `platform.gateway.internal.name` | `nebari-internal-gateway` | `nebari-gateway` |
| `platform.tls.clusterIssuer` | `letsencrypt-production` | `letsencrypt-issuer` |

If you set both values, nothing changes. If you left one unset and your
cluster relies on the old name, **set that one explicitly before
upgrading**. Add only the value you left unset; the example shows both:

```yaml
platform:
  gateway:
    internal:
      name: nebari-internal-gateway
  tls:
    clusterIssuer: letsencrypt-production
```

Without it, the operator moves the internal endpoint's route and listener
to `nebari-gateway`, or points the shared Certificate at an issuer your
cluster may not have, and it can no longer be renewed.

### Upgrading from 0.1.4 or earlier: the pack's namespace

The pack's namespace no longer follows `fullnameOverride` or `nameOverride`.
It is `global.namespace`, or, when that is empty,
`<release>-nebari-llm-serving-system` (`<release>-system` when the release
name contains `nebari-llm-serving`). Those two values now name resources only.

If neither was set, nothing changes. If either was set, your namespace was
named after it. **Set `global.namespace` to that namespace before
upgrading,** using the name the command below finds rather than working it
out from the override. Without it, the upgrade renders a Namespace
with a new name, and Helm (or Argo CD with automated prune) deletes the old
one, with the `LLMModel`s, the API keys and the provider Secrets in it.

Find the current namespace from the Namespace the chart created, which
carries the release name (under Argo CD, the Application's `releaseName`):

```bash
kubectl get namespace -l app.kubernetes.io/instance=<release>,nebari.dev/managed=true
```

If Argo CD tracks resources by label (the default before Argo CD 3.0), that
label holds the Application's name instead of `releaseName`; look up the
Application's name, or list `kubectl get namespace -l nebari.dev/managed=true`.

Then add it to your values, alongside the overrides you already set:

```yaml
global:
  namespace: llm-operator-system   # the namespace found above
```

Check the result before upgrading. The rendered Namespace must keep its
current name:

```bash
helm template <release> oci://quay.io/nebari/charts/nebari-llm-serving \
  --version <version> -f <your-values>.yaml | grep -A3 '^kind: Namespace'
```

Under Argo CD, `destination.namespace` must match `global.namespace`.

### Upgrading from 0.1.4 or earlier: Envoy AI Gateway 1.1

Releases after 0.1.4 emit `aigateway.envoyproxy.io/v1beta1` resources and target
the gateway versions above. An installation on 0.1.4 or earlier needs these
steps.

#### Existing provider settings

The operator translates the legacy `spec.provider.schemaVersion` setting into
Envoy's `schema.prefix`: `api/v1` still reaches `/api/v1/chat/completions`, and
the default remains `/v1`. Bedrock uses its own native paths without a prefix.
API schema versions and URL prefixes remain separate in the provider adapter.

Both served and external-provider routes use `aigateway.envoyproxy.io/v1beta1`.
Each endpoint declares its hostname, so `/v1/models` includes its own catalog
without depending on the other endpoint being enabled. Listener references and
per-model authentication remain in place. Hostname scoping is not user-level
catalog filtering; model invocation still enforces API-key scope and JWT groups.
Disabling a provider endpoint removes its route and catalog entries. Its auth
policy stays until the generated HTTPRoute is gone, and issued keys are preserved
for re-enabling the endpoint.

If the gateway is already on a supported release and only the pack is changing,
roll the AI Gateway controller after installing the new operator. This lets it
restore cleanup finalizers that older pack operators removed from its resources.

Provider hostnames are normalized to lowercase and have a single trailing DNS
root dot removed before gateway resources are generated. The stored spec is not
rewritten. Review existing `PassthroughModel.spec.provider.hostname` values before
upgrading: underscores, empty labels, URLs, ports, paths, and whitespace are
rejected. Older webhooks admitted some of these values; correct any remaining
invalid names before upgrading to avoid reconciliation failures.

#### Upgrade an installation on AI Gateway 0.5

Follow the upstream [controller upgrade policy](https://github.com/envoyproxy/ai-gateway/blob/v1.1.0/RELEASES.md#upgrading-the-envoy-ai-gateway-controller)
and [compatibility matrix](https://aigateway.envoyproxy.io/docs/compatibility/).
Use staged revisions, rather than changing every controller independently:

1. Record the current chart and operator revisions and inventory all gateway
   resources, including non-LLM routes on a shared gateway. Check the intervening
   Envoy Gateway release notes for policy changes. Keep CRDs during rollback;
   deleting them also deletes their resources.
2. Install the compatible Gateway API and Envoy Gateway CRDs and upgrade Envoy
   Gateway to %%pin:ENVOY_GATEWAY_VERSION%% using the official chart. CRD updates must be explicit:
   a Helm controller upgrade alone does not reliably update installed CRDs.
3. Before crossing AI Gateway 0.6, migrate any external OpenAI backends from
   `schema.version` to `schema.prefix`. If the old operator still reconciles
   these resources, pause that reconciler during the handover. Move any custom
   `AIGatewayRoute.spec.filterConfig` into `GatewayConfig`; this pack does not
   generate `filterConfig`.
4. Upgrade AI Gateway CRDs and controller to 0.7, then update the pack's CRDs as
   in the [routine steps](#routine-upgrade) and deploy the
   new pack operator. Until the CRDs are updated, the old `PassthroughModel`
   schema still requires a hostname and an API-key Secret and rejects the new
   backend and credential fields, so wait for the new operator and webhook
   before applying Bedrock resources. Version 0.7 supports hostname-scoped catalogs
   and the `v1beta1` resources the operator now emits. Confirm that all resources reconcile before
   proceeding to AI Gateway 1.1, using 1.0 as an intermediate controller release.
   AI Gateway 1.0 has a namespace-discovery bug when the Gateway lives in the
   Envoy Gateway controller's namespace: it cannot refresh the sidecar config.
   In that layout, retain the previous data-plane pod and proceed to 1.1, which
   [deduplicates the namespace lookup](https://github.com/envoyproxy/ai-gateway/blob/v1.1.0/internal/controller/gateway.go#L1353).
5. Roll the Envoy data plane after each AI Gateway controller upgrade so new pods
   receive its matching ext-proc sidecar. Use an `EnvoyProxy` pod-template
   annotation to request the rollout; do not edit generated Deployments. Preserve
   the ServiceAccount and cloud workload identity. With Argo CD, retain the
   cert-manager webhook certificate configuration.
6. Check both inference endpoints, model catalogs, streaming, rejected
   credentials, local `InferencePool` models, and non-LLM routes. Expect active
   connections to reconnect during a data-plane rollout. Only finish the upgrade
   when the desired GitOps revisions and actual pod images agree.

The `v1alpha1` AI Gateway API remains served upstream, but new writes use
`v1beta1`. Reapplying resources migrates their stored representation; do not
remove old CRD storage versions until every stored object has been migrated.

For rollback, restore compatible controller/operator revisions through GitOps
while retaining the installed CRDs. Returning to AI Gateway 0.5 also requires
restoring its path-prefix and catalog configuration; an image-only rollback is
not sufficient.

#### Scope of the upgrade

AI Gateway 1.1 makes newer protocol translation, token counting, streaming
controls, and tracing available. It does not automatically enable additional
providers, failover, or tracing, and does not grant cloud model access. Provider
adapters still select the appropriate upstream schema and authentication.

#### Check generated resources against upstream CRDs

The operator's `TestGatewayAdmission` uses a local Kubernetes API server with
the released AI Gateway CRDs. It checks admission and stored fields, including
path prefixes and hostname scoping. No cluster or cloud credentials are used.

Render `ai-gateway-crds-helm` version `%%pin:AI_GATEWAY_VERSION%%` into a temporary directory, set
`AI_GATEWAY_CRD_DIR` to that directory and `KUBEBUILDER_ASSETS` to the binaries
installed by `make setup-envtest`, then run from `operator`:

```sh
go test ./internal/controller/reconcilers -run TestGatewayAdmission -v
```

### Upgrading from 0.1.4 or earlier: a mirrored Endpoint Picker image

The operator now writes each model's built-in EPP config as
`llm-d.ai/v1alpha1`, which `llm-d-inference-scheduler:v0.8.0` cannot load. If
`defaults.epp.image` points at a mirror of that image, mirror
`ghcr.io/llm-d/llm-d-router-endpoint-picker:v0.9.0` and update the value before
upgrading.
