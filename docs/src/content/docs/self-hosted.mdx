A `PassthroughModel` can front an OpenAI-compatible server that you run on
another machine, such as llama.cpp's `llama-server` on a Mac Studio, vLLM on a
workstation, or LM Studio. Users keep the shared endpoints, their minted API
keys or Keycloak JWTs, and group access control. The server's own API key stays
with the platform. This page uses `llama-server` as the worked example.

## How the connection works

A request crosses two TLS connections:

```
client ──TLS──▶ gateway (llm.<baseDomain>) ──TLS──▶ self-hosted server
```

The gateway always uses TLS toward the provider and verifies the server's
certificate against `spec.provider.hostname`. By default it trusts only the
public CA roots built into the Envoy proxy image. A server whose certificate
comes from a private or corporate CA needs `spec.provider.tls.caConfigMapName`,
which points the gateway at a ConfigMap holding that CA.

## Requirements

- **Network reachability.** The Envoy proxy pods for the gateway (usually in
  `envoy-gateway-system`) must reach the server on its port. Open that port in
  the host firewall, such as the macOS application firewall.
- **A DNS name, not an IP address.** Envoy Gateway rejects IP addresses and
  single-label names such as `macstudio` as backend hostnames. Use a name like
  `macstudio.corp.example.com` that cluster DNS resolves. If your cluster DNS
  answers a whole zone with the gateway address (for example a wildcard for
  `*.<baseDomain>`), choose a name outside that zone. Check resolution from
  inside the cluster:

  ```sh
  kubectl run dnscheck --rm -it --restart=Never --image=busybox:1.36 -- \
    nslookup macstudio.corp.example.com
  ```

- **A server certificate for that name.** Its subject alternative names must
  include the hostname, and it must be signed with SHA-256 or stronger. Current
  TLS stacks reject SHA-1 signatures, and no trust setting changes that.
- **An API key** that the server requires on every request.

## 1. Prepare the certificate

Request a server certificate for the hostname from your CA. `llama-server` needs
two PEM files: the certificate followed by any intermediate CAs, and an
unencrypted private key. If your CA delivers a PKCS#12 (`.pfx`) bundle, split it:

```sh
openssl pkcs12 -in macstudio.pfx -nokeys -out macstudio.crt
openssl pkcs12 -in macstudio.pfx -nocerts -nodes -out macstudio.key
chmod 600 macstudio.key
```

OpenSSL 3 needs `-legacy` for bundles that use older encryption. Check the
name and signature before going further:

```sh
openssl x509 -in macstudio.crt -noout -ext subjectAltName
openssl x509 -in macstudio.crt -noout -text | grep -m1 'Signature Algorithm'
```

Keep the CA certificate that signed it (here `corp-root-ca.pem`); the cluster
needs it in step 3.

## 2. Run llama-server with TLS and an API key

Install llama.cpp with OpenSSL support. The Homebrew formula
(`brew install llama.cpp`) has it; source builds enable it by default with
`-DLLAMA_OPENSSL=ON`. Generate a key and start the server:

```sh
openssl rand -hex 32 > api-key
chmod 600 api-key

llama-server -hf <hf-user>/<model>-GGUF:Q4_K_M \
  --alias qwen3-30b-a3b \
  --host 0.0.0.0 --port 8443 \
  --ssl-cert-file macstudio.crt \
  --ssl-key-file macstudio.key \
  --api-key-file api-key \
  --no-webui
```

- `--alias` sets the model id the server reports. Declare the same id in the
  `PassthroughModel`.
- `--api-key-file` reads one key per line. Requests without a matching
  `Authorization: Bearer` header get HTTP 401; only `/health` stays public.
- `--no-webui` turns off the built-in chat page, whose static assets do not
  require the key.
- A build without SSL refuses to start with
  `the server is built without SSL support`.

Run it under `launchd` or another supervisor so it survives logouts and
reboots. From any machine that trusts the CA, confirm TLS and the key:

```sh
curl --cacert corp-root-ca.pem \
  -H "Authorization: Bearer $(cat api-key)" \
  https://macstudio.corp.example.com:8443/v1/models
```

## 3. Store the key and the CA in the cluster

Create both objects in the PassthroughModel's namespace, which is the operator
namespace. Command substitution strips the file's trailing newline, which
would otherwise become part of the key:

```sh
kubectl create secret generic macstudio-api-key -n nebari-llm-serving-system \
  --from-literal=apiKey="$(cat api-key)"
kubectl create configmap corp-ca -n nebari-llm-serving-system \
  --from-file=ca.crt=corp-root-ca.pem
```

The ConfigMap must hold the CA under the `ca.crt` key or as its only key. A
trust-manager Bundle target that already projects your organization's CAs into
the namespace qualifies; reference it by name instead of creating `corp-ca`.

The bundle **replaces** the public roots for this provider only. Other
PassthroughModels keep the public roots. Envoy Gateway watches the ConfigMap, so
renewing the CA takes effect without restarting the gateway.

## 4. Apply the PassthroughModel

An existing cluster needs the pack release that adds `spec.provider.tls` to the
`PassthroughModel` CRD, and the matching operator, before applying this
manifest. An older CRD drops or rejects the field, and an older operator keeps
trusting only the public roots. Helm does not upgrade installed CRDs; see
[Upgrade the pack's CRDs with plain Helm](/gateway-upgrades/#upgrade-the-packs-crds-with-plain-helm).

## 5. Verify

```sh
kubectl -n nebari-llm-serving-system get passthroughmodel macstudio
kubectl -n nebari-llm-serving-system get backendtlspolicy macstudio-backend-tls \
  -o jsonpath='{range .status.ancestors[*].conditions[*]}{.type}={.status} {.reason}: {.message}{"\n"}{end}'

curl https://llm.your-cluster.example.com/v1/chat/completions \
  -H "Authorization: Bearer sk-your-api-key" \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen3-30b-a3b", "messages": [{"role": "user", "content": "Hello"}]}'
```

The PassthroughModel reports `Ready` once its resources are applied. Readiness
does not mean the server is reachable. The `BackendTLSPolicy` status reports a
missing or empty CA ConfigMap. Handshake failures appear only on requests; see
[Troubleshooting](/troubleshooting/#external-provider-passthroughmodel-not-working).

## Limits

- **120-second request timeout.** Passthrough routes use a fixed 120s timeout
  for the whole response, streamed or not. A slow local model can be cut off
  during long generations; cap `max_tokens` accordingly.
- **One address per PassthroughModel.** The gateway sends every request to the
  single hostname and port, without load balancing or failover. When the
  server is down, requests fail at the gateway.
- **The server sees the platform key, not users.** Per-user identity, access
  groups, and key revocation are enforced at the gateway.
